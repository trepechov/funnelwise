# Spike 0.4: write guard on Desktop

Question: do plugin `PreToolUse` hooks run in Cowork, and can a plugin stop third-party connector
tools (posting, deleting, messaging)?

## Built (Phase 2.5)

`hooks/write_guard.py` runs before every `mcp__*` tool:
- **Write guard**: for servers that look like marketing platforms (ours, the pinned third-party
  servers, Metricool, Windsor, …), denies tools whose action verb writes (post, publish, schedule,
  reply, delete, send, upload, update, …). The verb is the first word after any platform prefix,
  so `get_post_comments` passes and `youtube_post_comment` doesn't. camelCase names are handled.
- **Scope guard**: denies account arguments that point outside `brand.yaml` (another site,
  property, show, channel, Page), and YouTube `mine: true`. That covers third-party and easy-path
  tools, which our servers can't scope themselves.
- It never blocks because of its own failure (bad JSON, broken brand.yaml → write guard only).

Our own servers have no write tools at all, so they are read-only even where hooks don't run.

## Verified

- Unit tests over the real tool lists of facebook-mcp-server (40 tools), youtube-studio-mcp (40),
  ig-mcp (10) and Metricool's published names: every write tool is denied, every read tool allowed,
  non-marketing tools (GitHub, Drive, our own `fw_*`) untouched (`tests/test_hooks.py`).
- Hook process contract: JSON on stdin → `permissionDecision: deny` JSON on stdout, exit 0.

## Open

- **Does the hook run in Cowork?** 0.1 finding #1 says hooks load in Cowork tasks on the user's
  computer (seen with another plugin). Not yet observed for Funnelwise. Test: in a Cowork task with
  Metricool connected, ask "schedule a post saying test for tomorrow". Expected: denied with the
  read-only message. Also try Claude Code.
- **In plain chat** (no hooks), Metricool's scheduling tools would be callable. Mitigations already
  in place: onboarding warns once; skills never call write tools; Metricool's own permissions can
  be limited. If Cowork doesn't run the hook either, add that as an explicit risk in onboarding and
  consider recommending a read-only Metricool user.
